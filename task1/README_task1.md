## 1) Сравнение LLM (локальные HF vs OpenAI/YandexGPT)

### Локальные модели (Hugging Face / llama.cpp / vLLM)
- **Плюсы**:
  - Контроль данных (on‑prem), удобнее для строгих требований безопасности.
  - Предсказуемая стоимость при высокой нагрузке.
  - Возможность тюнинга под домен (при наличии экспертизы).
- **Минусы**:
  - Для хорошей скорости нужен GPU и инфраструктура.
  - Качество “из коробки” у малых моделей ниже флагманских облачных.
  - Выше сложность эксплуатации/обновлений.

### OpenAI (облако)
- **Плюсы**:
  - Лучшее качество генерации и устойчивость поведения в RAG.
  - Быстрый старт через API, масштабирование без DevOps‑нагрузки.
- **Минусы**:
  - Данные (хотя бы запрос/контекст) уходят во внешний сервис.
  - Стоимость линейно растёт с использованием.

### YandexGPT (облако)
- **Плюсы**:
  - Сильный вариант для RU/EN сценариев, удобен в “локальной” экосистеме.
- **Минусы**:
  - На сложных задачах рассуждений может уступать топ‑моделям OpenAI.

### Итог по LLM
Для MVP и пилота — **облачная LLM** (быстрее и дешевле в запуске). Для продакшена при росте требований безопасности/нагрузки — предусмотреть возможность миграции на локальную LLM.

> **Примечание про локальную разработку**: для разработки можно использовать Ollama + Mistral (без ключей, удобно для отладки), а для продакшена переключаться на OpenAI API.

## 2) Сравнение эмбеддингов (Sentence‑Transformers vs OpenAI embeddings)

### Локальные Sentence‑Transformers
- **Плюсы**:
  - Данные не уходят во внешний сервис.
  - Дешевле на больших объёмах и при частой переиндексации.
  - Можно подобрать модель под язык/домен.
- **Минусы**:
  - Требуют ресурсов (CPU/GPU) и поддержки окружения.
  - Качество зависит от выбранной модели.

### Облачные эмбеддинги (OpenAI)
- **Плюсы**:
  - Стабильное качество “из коробки”, минимум поддержки.
  - Удобно для быстрого MVP.
- **Минусы**:
  - Стоимость за токены, зависимость от сети/лимитов.

### Итог по эмбеддингам
Для роста объёма корпоративной документации и контроля стоимости/данных — **локальные эмбеддинги** (Sentence‑Transformers). Для MVP допустимы облачные.

## 3) Векторное хранилище (ChromaDB vs FAISS)

### FAISS
- **Плюсы**: максимальная скорость, гибкость индексов, легковесность.
- **Минусы**: метаданные/персистентность/фильтрацию часто надо “достраивать” вручную.

### ChromaDB
- **Плюсы**: удобное API, персистентность, метаданные и фильтрация “из коробки”, проще инкрементальные обновления.
- **Минусы**: меньше контроля над низкоуровневыми деталями, возможны проблемы совместимости persist‑форматов между версиями.

### Итог по векторной БД
Для проектной работы и MVP: **ChromaDB** (быстрее внедрить, проще сопровождать, есть метаданные).

## 4) Рекомендуемая инфраструктура (варианты)

### Вариант A — MVP (облако для LLM/эмбеддингов)
- CPU: 4–8 vCPU, RAM: 8–16 GB, SSD: 100+ GB.
- Быстро и дёшево стартовать, но данные уходят в облако.

### Вариант B — гибрид (рекомендовано для продакшена)
- Эмбеддинги локально, LLM — облако.
- CPU: 8–12 vCPU, RAM: 16–24 GB, SSD: 200+ GB.
- Опционально GPU для ускорения индексации.

### Вариант C — полностью локально (макс. конфиденциальность)
- CPU 16+ vCPU, RAM 32+ GB, GPU (для комфортного инференса LLM).
- Сложнее/дороже, оправдано при строгих требованиях.

## Финальный выбор для проекта (с учётом целей QuantumForge)

- **Векторная БД**: ChromaDB
- **Эмбеддинги**: Sentence‑Transformers локально (например, all‑MiniLM‑L6‑v2)
- **LLM**:
  - для разработки: Ollama + Mistral
  - для продакшена: облачная LLM (OpenAI) с возможностью переключения/миграции
