# Задание 1. Исследование моделей и инфраструктуры

Подробный анализ по выбору LLM, модели эмбеддингов, векторного хранилища и инфраструктуры для RAG‑бота QuantumForge Software.

## Контекст кейса

- Компания: QuantumForge Software (EU, важно учитывать требования уровня GDPR и чувствительность инженерной/внутренней документации).
- Данные: много документов (репозитории/Confluence/PDF), регулярный прирост.
- Цель: RAG‑бот для сотрудников (разработчики, саппорт, менеджеры/аналитики, онбординг).

## 1. Сравнение LLM (локальные HF vs OpenAI/YandexGPT)

### Локальные модели (Hugging Face / llama.cpp / vLLM)
- **Плюсы**:
  - Контроль данных (on‑prem), удобнее для строгих требований безопасности.
  - Предсказуемая стоимость при высокой нагрузке.
  - Возможность тюнинга под домен (при наличии экспертизы).
- **Минусы**:
  - Для хорошей скорости нужен GPU и инфраструктура.
  - Качество "из коробки" у малых моделей ниже флагманских облачных.
  - Выше сложность эксплуатации/обновлений.

### OpenAI (облако)
- **Плюсы**:
  - Лучшее качество генерации и устойчивость поведения в RAG.
  - Быстрый старт через API, масштабирование без DevOps‑нагрузки.
- **Минусы**:
  - Данные (хотя бы запрос/контекст) уходят во внешний сервис.
  - Стоимость линейно растёт с использованием.

### YandexGPT (облако)
- **Плюсы**:
  - Сильный вариант для RU/EN сценариев, удобен в "локальной" экосистеме.
- **Минусы**:
  - На сложных задачах рассуждений может уступать топ‑моделям OpenAI.

### Итог по LLM
Для MVP и пилота — **облачная LLM** (быстрее и дешевле в запуске). Для продакшена при росте требований безопасности/нагрузки — предусмотреть возможность миграции на локальную LLM.

> **Примечание про локальную разработку**: для разработки можно использовать Ollama + Mistral (без ключей, удобно для отладки), а для продакшена переключаться на OpenAI API.

## 2. Сравнение эмбеддингов (Sentence‑Transformers vs OpenAI embeddings)

### Локальные Sentence‑Transformers
- **Плюсы**:
  - Данные не уходят во внешний сервис.
  - Дешевле на больших объёмах и при частой переиндексации.
  - Можно подобрать модель под язык/домен.
- **Минусы**:
  - Требуют ресурсов (CPU/GPU) и поддержки окружения.
  - Качество зависит от выбранной модели.

### Облачные эмбеддинги (OpenAI)
- **Плюсы**:
  - Стабильное качество "из коробки", минимум поддержки.
  - Удобно для быстрого MVP.
- **Минусы**:
  - Стоимость за токены, зависимость от сети/лимитов.

### Итог по эмбеддингам
Для роста объёма корпоративной документации и контроля стоимости/данных — **локальные эмбеддинги** (Sentence‑Transformers). Для MVP допустимы облачные.

## 3. Векторное хранилище (ChromaDB vs FAISS)

### 3.1 Скорость поиска и индексации

**FAISS (Facebook AI Similarity Search):**
- **Скорость поиска:**
  - Очень высокая скорость поиска по индексу (миллисекунды для миллионов векторов)
  - Оптимизированные алгоритмы индексации (IVF, HNSW, LSH)
  - Поддержка GPU-ускорения для больших объёмов данных
  - Эффективная работа с большими батчами запросов
- **Скорость индексации:**
  - Быстрое построение индекса при использовании GPU
  - На CPU индексация может быть медленной для очень больших корпусов
  - Требуется переиндексация при добавлении новых документов (в зависимости от типа индекса)
- **Особенности:**
  - Библиотека низкого уровня, оптимизированная для производительности
  - Поддержка различных метрик расстояния (L2, косинусное расстояние, внутреннее произведение)

**ChromaDB:**
- **Скорость поиска:**
  - Хорошая скорость для средних объёмов данных (до нескольких миллионов векторов)
  - Оптимизированные алгоритмы поиска под капотом
  - Может быть медленнее FAISS на очень больших объёмах
- **Скорость индексации:**
  - Инкрементальная индексация — можно добавлять векторы без полной переиндексации
  - Автоматическая оптимизация индекса
  - Удобная работа с динамически обновляемой базой знаний
- **Особенности:**
  - Встроенная персистентность (данные сохраняются на диск)
  - Поддержка метаданных и фильтрации по ним
  - Автоматическое управление индексами

**Вывод:**  
FAISS превосходит по скорости поиска на больших объёмах данных и при использовании GPU. ChromaDB удобнее для инкрементальных обновлений и работы с метаданными, но может быть медленнее на очень больших корпусах.

### 3.2 Сложность внедрения и поддержки

**FAISS:**
- **Сложность внедрения:**
  - Требуется написание кода для управления индексами и векторами
  - Необходимо самостоятельно реализовывать персистентность (сохранение/загрузка индексов)
  - Нет встроенной поддержки метаданных — нужно хранить их отдельно
  - Требуется понимание различных типов индексов и их параметров
- **Поддержка:**
  - Минимальная инфраструктура (библиотека Python/C++)
  - Необходимо самостоятельно управлять версионированием индексов
  - Требуется мониторинг использования памяти и производительности
- **Преимущества:**
  - Полный контроль над процессом индексации и поиска
  - Легковесное решение без зависимостей от внешних сервисов
  - Хорошая интеграция с LangChain и другими фреймворками

**ChromaDB:**
- **Сложность внедрения:**
  - Простая установка и настройка (pip install chromadb)
  - Встроенная персистентность и управление коллекциями
  - Удобный API для работы с метаданными и фильтрацией
  - Можно использовать как встроенную БД или как отдельный сервис
- **Поддержка:**
  - Автоматическое управление индексами и оптимизация
  - Встроенное версионирование и бэкапы
  - Проще мониторить и отлаживать через встроенные инструменты
- **Преимущества:**
  - Меньше кода для написания и поддержки
  - Встроенная поддержка метаданных и фильтрации
  - Хорошая интеграция с LangChain
- **Недостатки:**
  - Дополнительная зависимость (отдельный сервис или библиотека)
  - Меньше гибкости в настройке алгоритмов поиска

**Вывод:**  
ChromaDB значительно проще во внедрении и поддержке благодаря встроенным возможностям. FAISS требует больше кода и экспертизы, но даёт больше контроля и гибкости.

### 3.3 Удобство в работе

**FAISS:**
- **Плюсы:**
  - Легковесная библиотека без внешних зависимостей
  - Гибкость в выборе алгоритмов индексации
  - Хорошая производительность "из коробки"
  - Широкое использование в индустрии
- **Минусы:**
  - Нужно самостоятельно управлять сохранением/загрузкой индексов
  - Нет встроенной поддержки метаданных
  - Требуется больше кода для базовых операций
  - Сложнее отлаживать проблемы с индексами

**ChromaDB:**
- **Плюсы:**
  - Простой и интуитивный API
  - Встроенная поддержка метаданных и фильтрации
  - Автоматическая персистентность
  - Удобные инструменты для отладки и мониторинга
  - Поддержка коллекций и пространств имён
- **Минусы:**
  - Меньше контроля над внутренними алгоритмами
  - Дополнительная зависимость в проекте
  - Может быть избыточным для простых случаев

**Вывод:**  
ChromaDB удобнее для разработки и повседневной работы благодаря простому API и встроенным возможностям. FAISS требует больше ручной работы, но даёт больше контроля.

### 3.4 Стоимость владения (учёт инфраструктуры)

**FAISS:**
- **Инфраструктура:**
  - Минимальные требования: библиотека работает на том же сервере, что и приложение
  - Для больших объёмов может потребоваться дополнительная RAM или GPU
  - Хранение индексов на диске (размер зависит от типа индекса и количества векторов)
- **Эксплуатация:**
  - Нет дополнительных сервисов для поддержки
  - Затраты только на инфраструктуру (CPU/RAM/GPU/диск)
  - Необходимо учитывать время разработки и поддержки кода
- **Масштабирование:**
  - Линейное масштабирование с ростом данных
  - Возможность распределённого поиска (при использовании FAISS в кластере)
- **Расчёт для кейса QuantumForge:**
  - ~18,000 документов + ~3,000 страниц Confluence + ~250 PDF
  - При среднем размере чанка 500 токенов и размерности эмбеддинга 1536: ~50-100 MB индекса
  - Минимальные требования: 2-4 GB RAM для индекса + приложение
  - Стоимость инфраструктуры: включена в общую стоимость сервера

**ChromaDB:**
- **Инфраструктура:**
  - Можно использовать как встроенную БД (минимальные требования)
  - Или как отдельный сервис (требует дополнительных ресурсов)
  - Хранение данных на диске с автоматическим управлением
- **Эксплуатация:**
  - Проще в поддержке благодаря встроенным инструментам
  - Меньше времени на разработку и отладку
  - Автоматическое управление индексами снижает операционные затраты
- **Масштабирование:**
  - Поддержка кластерного режима для больших объёмов
  - Автоматическая оптимизация использования ресурсов
- **Расчёт для кейса QuantumForge:**
  - Аналогичные требования к ресурсам
  - Дополнительные ~500 MB RAM для сервиса ChromaDB (если используется как отдельный сервис)
  - Стоимость: включена в общую стоимость сервера + немного больше операционных затрат

**Вывод:**  
Оба решения имеют схожую стоимость владения на уровне инфраструктуры. FAISS требует больше времени на разработку и поддержку кода, ChromaDB — немного больше ресурсов, но меньше времени разработчиков.

### 3.6 Рекомендации для QuantumForge Software

**Рекомендуемый выбор: ChromaDB**

**Обоснование:**
1. **Удобство разработки:** Простой API и встроенные возможности ускорят разработку MVP
2. **Инкрементальные обновления:** База знаний растёт (~400 страниц/месяц), ChromaDB удобнее для регулярных обновлений
3. **Метаданные:** Важно хранить информацию о источнике (Confluence, GitHub, PDF), ChromaDB поддерживает это из коробки
4. **Поддержка:** Меньше кода = меньше багов и проще поддержка
5. **Производительность достаточна:** Для текущего объёма данных (~21,000 документов) скорость ChromaDB более чем достаточна

**Альтернатива: FAISS**
- Рассмотреть при росте до миллионов документов
- Если критична максимальная скорость поиска
- Если нужен полный контроль над алгоритмами индексации

## 4. Рекомендуемая конфигурация сервера для RAG-бота

### 4.1 Анализ требований

**Требования к системе:**
- Объём данных: ~21,000 документов (18,000 Markdown + 3,000 Confluence + 250 PDF)
- Размер эмбеддингов: 1536 измерений (OpenAI) или 384-768 (Sentence-Transformers)
- Ожидаемая нагрузка: 100-500 запросов в день (внутренний корпоративный бот)
- Требования к конфиденциальности: работа с потенциально чувствительными данными

**Компоненты системы:**
1. **Векторная БД (ChromaDB/FAISS):** хранение и поиск эмбеддингов
2. **Модель эмбеддингов:** генерация векторов (локально или через API)
3. **LLM:** генерация ответов (локально или через API)
4. **Приложение:** RAG-пайплайн, API, бот (Telegram/веб)

---

### 4.2 Варианты конфигураций

**Вариант 1: Минимальная конфигурация (MVP, облачные сервисы)**

**Конфигурация:**
- **CPU:** 4 ядра (Intel Xeon или AMD EPYC)
- **RAM:** 8 GB
- **Диск:** 100 GB SSD
- **GPU:** не требуется
- **Сеть:** стабильное интернет-соединение

**Использование:**
- ChromaDB (встроенный режим) для векторной БД
- OpenAI Embeddings API для генерации эмбеддингов
- OpenAI GPT-4.1 nano или GPT-5 mini API для генерации ответов (экономичные модели с хорошим качеством)
- Python приложение с FastAPI

**Оценка стоимости:**
- Сервер (аренда): ~$50-100/месяц (AWS t3.large, DigitalOcean, Hetzner)
- OpenAI API (GPT-4.1 nano): ~$3-10/месяц или GPT-5 mini: ~$5-15/месяц (при 500 запросах/день, ~700 токенов/запрос)
- **Итого:** ~$53-110/месяц (GPT-4.1 nano) или ~$55-115/месяц (GPT-5 mini)

**Плюсы:**
- Минимальные начальные затраты
- Быстрое развёртывание
- Не требует GPU
- Простое масштабирование

**Минусы:**
- Зависимость от интернета и внешних API
- Данные уходят в облако (проблема конфиденциальности)
- Стоимость растёт с нагрузкой

### 4.3 Итоговая рекомендация по конфигурации

**Для MVP (начальный этап):**

**Для продакшена (рекомендуется):**
- **Вариант 4:** Гибридная конфигурация

## 5. Итоговые рекомендации для QuantumForge Software

### 5.1 Сравнение вариантов решения

**Вариант A: Облачное решение (быстрый старт)**

**Стек:**
- LLM: OpenAI GPT-4.1 nano (минимальная стоимость) или GPT-5 mini (баланс качества и стоимости) или GPT-5.2 (максимальное качество)
- Эмбеддинги: OpenAI Embeddings
- Векторная БД: ChromaDB (встроенный режим)
- Инфраструктура: облачный сервер (8 GB RAM, 4 CPU)

**Плюсы:**
- Минимальные затраты на старт (~$53-110/месяц с GPT-4.1 nano, ~$55-115/месяц с GPT-5 mini)
- Быстрое развёртывание (1-2 недели)
- Простота поддержки
- Автоматическое масштабирование
- GPT-4.1 nano — самая экономичная модель для простых RAG-запросов
- GPT-5 mini — отличный баланс качества и стоимости

**Минусы:**
- Данные уходят в облако (проблема конфиденциальности)
- Стоимость растёт с нагрузкой
- Зависимость от внешних сервисов

**Оценка:** ⭐⭐⭐⭐ (4/5) — отлично для MVP

---

**Вариант B: Гибридное решение (рекомендуется)**

**Стек:**
- LLM: OpenAI GPT-4.1 nano, GPT-5 mini или GPT-4.1 mini (с возможностью миграции на локальную или fine-tuning)
- Эмбеддинги: Sentence-Transformers (локально)
- Векторная БД: ChromaDB
- Инфраструктура: облачный сервер (16 GB RAM, 8 CPU, опционально GPU)

**Плюсы:**
- Эмбеддинги и векторная БД локально (конфиденциальность поиска)
- Баланс стоимости и безопасности (~$203-360/месяц с GPT-4.1 nano, ~$205-365/месяц с GPT-5 mini, ~$208-375/месяц с GPT-4.1 mini)
- Гибкость в выборе LLM (GPT-4.1 nano для экономии, GPT-5 mini для баланса, GPT-4.1 mini для fine-tuning)
- Возможность fine-tuning GPT-4.1 mini на корпоративной документации для улучшения качества
- Возможность миграции на полностью локальное решение
- GPT-4.1 nano — самая экономичная модель для RAG-задач

**Минусы:**
- Требует больше настройки
- Зависимость от OpenAI API для генерации

**Оценка:** ⭐⭐⭐⭐⭐ (5/5) — оптимально для продакшена

---

**Вариант C: Локальное решение (максимальная безопасность)**

**Стек:**
- LLM: Mistral 7B или Llama 2 13B (локально на GPU)
- Эмбеддинги: Sentence-Transformers (локально на GPU)
- Векторная БД: ChromaDB
- Инфраструктура: GPU сервер (32 GB RAM, 16 CPU, NVIDIA A100/V100)

**Плюсы:**
- Полная конфиденциальность данных
- Нет зависимости от внешних сервисов
- Контроль над всей системой
- Окупается при высокой нагрузке (>1000 запросов/день)

**Минусы:**
- Высокая стоимость (~$1,500-3,000/месяц)
- Сложность настройки и поддержки
- Требует ML/DevOps экспертизы

**Оценка:** ⭐⭐⭐ (3/5) — оправдано при строгих требованиях к безопасности

---

**Вариант D: Экономичное локальное решение**

**Стек:**
- LLM: OpenAI GPT-4.1 nano или GPT-5 mini (API) — экономичные модели с хорошим качеством
- Эмбеддинги: Sentence-Transformers (локально на CPU)
- Векторная БД: FAISS (для максимальной производительности)
- Инфраструктура: сервер (16 GB RAM, 8 CPU)

**Плюсы:**
- Эмбеддинги локально
- FAISS для максимальной скорости поиска
- Средняя стоимость (~$153-280/месяц с GPT-4.1 nano, ~$155-285/месяц с GPT-5 mini)
- Хорошая производительность поиска
- GPT-4.1 nano — самая экономичная модель OpenAI

**Минусы:**
- Больше кода для поддержки FAISS
- Зависимость от OpenAI API
- Медленнее индексация на CPU

**Оценка:** ⭐⭐⭐⭐ (4/5) — хороший компромисс

### 5.2 Финальная рекомендация

**Рекомендуемый вариант: Вариант B (Гибридное решение)**

**Обоснование:**

1. **Конфиденциальность:** Эмбеддинги и векторная БД остаются локально, что защищает основную часть данных от утечек. В облако уходят только запросы и ответы LLM.

2. **Стоимость:** Баланс между начальными затратами и долгосрочной экономией. При росте нагрузки локальные эмбеддинги становятся выгоднее облачных.

3. **Гибкость:** Возможность начать с облачной LLM и мигрировать на локальную при необходимости без изменения остального пайплайна.

4. **Простота:** ChromaDB упрощает разработку и поддержку по сравнению с FAISS.

5. **Масштабируемость:** Решение легко масштабируется при росте компании и объёма данных.

**План внедрения:**

1. **Этап 1 (MVP, 1-2 месяца):**
   - Развёртывание на минимальной конфигурации (Вариант A)
   - Использование GPT-4.1 nano или GPT-5 mini для экономии
   - Тестирование с реальными пользователями
   - Сбор метрик и обратной связи

2. **Этап 2 (Продакшен, 3-6 месяцев):**
   - Миграция на гибридное решение (Вариант B)
   - Локальные эмбеддинги + облачная LLM (GPT-5 mini или GPT-4.1 mini)
   - Рассмотреть fine-tuning GPT-4.1 mini на корпоративной документации для улучшения качества
   - Настройка мониторинга и бэкапов

3. **Этап 3 (Оптимизация, 6+ месяцев):**
   - Оценка результатов fine-tuning и необходимости доработки
   - Оценка необходимости миграции на локальную LLM или использование GPT-5.2 для сложных запросов
   - Оптимизация производительности и стоимости
   - Масштабирование при росте нагрузки

### 5.3 Выбор векторной БД

**Рекомендация: ChromaDB**

**Обоснование:**
- Удобство разработки и поддержки
- Встроенная поддержка метаданных (важно для отслеживания источников)
- Инкрементальные обновления (база знаний растёт)
- Производительность достаточна для текущего объёма данных
- Хорошая интеграция с LangChain

**Альтернатива:** FAISS — рассмотреть при росте до миллионов документов или при требованиях к максимальной скорости поиска.
